# Review-only workflow

Process the single work object from preflight. Do not discover more PRs in
the agent session. Use the review plan generated by `build_context.py` and
the dimensional-review skill. Hand findings to this workflow's evidence and
verifier pipeline instead of posting directly. Never implement a finding. Use
bot_status_update with this instance ID at cycle start and end.

## Task state

- Key: preflight's task_key (review-only:github:<owner>/<repo>#<number>).
- Source type: github. Repository: preflight's repo_key.
- New PR: check task_check_capacity with instance_id, then task_add with
  external_key=task_key, source_type="github", instance_id,
  repo=repo_key, branch=head_branch, title=title, status="in_progress",
  PR URL in
  metadata.prs=[{"repo": "<owner>/<repo>", "number": <number>,
  "url": "<PR URL>", "host": "github"}], and the preflight head/base SHAs.
  Persist any supplied `review_label_event_id`, `review_authorization`,
  `review_approval_id`, `review_approval_response_comment_id`, and
  `review_approval_responder` in task metadata. Set
  `active_head_sha` and `active_base_sha` to the preflight SHA pair.
  If add fails, stop without posting.
- Existing task: task_get with key and source type, then task_update to
  in_progress for a new head/base pair or an authorized re-review request.
  Set `active_head_sha` and `active_base_sha` to the preflight pair and persist
  all supplied authorization fields. Do not claim another instance's task.
- Before setting an existing task to `in_progress`, verify its current status
  with `task_get`. If it is `paused`, stop without changing the task or
  starting model work.
- Authorization gate: for `kind="review"`, preflight must supply either
  `review_authorization="label_added"` or
  `review_authorization="organization_member_approved"`. If neither is
  present, stop before context building or any model call. A label event ID
  means the configured review label was newly added; a currently present
  label alone does not authorize a review. Persist the event ID on the task so
  it cannot authorize another pass. SHA changes and `/review-bot re-review`
  requests need an organization member's explicit `Review bot: yes <RA-ID>`
  response to the marked PR comment. The approval is bound to the exact head
  and base SHAs in that request. A pending or declined approval is not review
  work; preflight continues with other PRs. An interrupted, already-authorized
  task resumes without asking again.
- Save last_step and next_step at milestones. When a review is posted,
  update to pr_open with last_reviewed_sha, last_reviewed_base_sha,
  last_reviewed_at, last_seen_updated_at, review URL, review_id, update_count,
  and context manifest path. These fields let the next cycle find and update
  the same review instead of posting a new one. Do not persist a local
  `ledger_path` as durable state.
- `pr_open` means the review is complete and the pull request is awaiting
  changes or merge. It is active task state, but preflight must not resume it
  unless the PR changes or new feedback arrives. Set `done` only after GitHub
  confirms a non-null `mergedAt` for the pull request.
- `review_id` and `update_count` exist from the task's first posted review
  onward; a task with no `review_id` yet has never posted. The status review
  body is the durable ledger source. Preflight checks that review first, then
  checks a recoverable pending publication and the legacy local ledger. It
  writes the recovered data to a temporary `work.ledger_path`; the next cycle
  restores the ledger from GitHub again. If an existing review has no ledger
  in any recoverable location, preflight posts one marked comment asking
  whether to start a fresh review. Any member of the PR repository's GitHub
  organization can respond; preflight verifies membership before accepting
  the response. The comment may contain `Review bot: yes <recovery-id>` or
  `Review bot: no <recovery-id>` along with other text. A verified yes starts
  a fresh review with update count 0. A verified no or no response leaves the
  PR waiting. Preflight then scans for another eligible PR, so waiting for a
  decision does not block other tasks. If membership cannot be verified, the
  response is not accepted and preflight still moves on to other work. An
  empty bot-owned pending review on the current head with no inline comments
  can be reused after approval. If that empty draft targets an older head,
  preflight sets `work.ignore_review_id`; clear the old `review_id` and omit
  `--review-id` so the new review is published separately. Pending reviews
  with content or inline comments still require manual reconciliation.
- When preflight supplies `ledger_recovery_approved`, an organization member
  approved starting over because the old ledger could not be recovered. Run a
  fresh review with `update_count=0`; do not claim to have carried old finding
  IDs forward. If `work.ignore_review_id` is true, set the task's old
  `review_id` and `review_url` to null and do not pass `--review-id` to the
  publisher.
- `seen_rereview_comment_ids` records processed command comment IDs;
  `seen_feedback_comment_ids` records human conversation/review comment IDs
  seen at the timestamp boundary; `pending_publication` records a validated
  but unfinished publication. Treat missing fields as empty lists and null,
  respectively, for existing tasks.
- Archived task records keep their unique `external_key`. Preflight includes
  them when matching PRs and skips archived PRs, so a still-present GitHub
  label cannot cause a duplicate `task_add`. To resume, unarchive that task
  record; do not create a replacement task for the same PR.
- Paused tasks are hard-skipped by preflight. Do not run review, feedback,
  comment handling, or lifecycle reconciliation for a task whose status is
  `paused`, even when its PR changes, receives comments, or reopens. Only an
  operator changing the task status from `paused` can resume it.
- Re-read task state before context building, before each model batch, before
  verification, before every `task_update`, and immediately before any GitHub
  publication. If the task is
  `paused`, stop at that point: launch no more workers, post no comments, and
  do not update the task or change its status. If a parallel batch is already
  running, do not start another; stop after that batch returns. Set only the
  bot activity status to idle and report that the task is paused.
  At cycle entry, check task state before marking the task working or changing
  its status.
  If `task_get` fails or returns an unreadable status at a checkpoint, stop
  before further model work or publication and leave the task unchanged.

## PR lifecycle-only work

Preflight can select `merge_complete`, `closed_unmerged`, or `reconcile_open`
work without requesting another review, but never selects a task already
marked `paused`. Handle lifecycle work before building review context. Re-read
the PR with
`gh pr view <number> --repo <owner>/<repo> --json state,mergedAt,closedAt,headRefOid,baseRefOid,updatedAt`.

- If `mergedAt` is non-null, set status to `done`, record
  `metadata.pr_lifecycle="merged"` and `metadata.merged_at`, and clear any
  `paused_reason`.
- If the PR state is `OPEN`, set status to `pr_open`, record
  `metadata.pr_lifecycle="open"`, and clear any `paused_reason`. Preserve the
  feedback watermark so unseen comments remain eligible for a later check.
- If the PR state is `CLOSED` and `mergedAt` is null, set status to `paused`,
  set `paused_reason="PR closed without merge"`, and record
  `metadata.pr_lifecycle="closed_unmerged"`, `paused_sha`,
  `paused_base_sha`, and `last_seen_updated_at` from the live PR.

Do not review, post comments, or mark a PR done in these lifecycle-only paths.
If the GitHub lookup fails or returns an unknown state, leave the task unchanged
and report the failure. A closed, unmerged PR remains not done. Its task is
paused; reopening the PR does not resume it. An operator must unpause the task
before lifecycle or review work can continue.

## Review or resume

At the start of a new review, check for re-review commands in the preflight
time window as described under **Feedback check**. Commands do not authorize a
review by themselves: preflight asks for approval, and only a verified
organization-member yes response makes the work eligible. A fresh event adding
the configured review label is the only automatic full-review trigger. A
review already triggered by a label-add event also satisfies any authorized
commands in that window; record their IDs for the cycle. Save the preflight `updated_at` as this cycle's
watermark. Do not add comments arriving later to the current cycle: the next
feedback check must see them.

If `pending_publication` exists and its head/base match the preflight pair,
resume from step 6 using its validated publication JSON, inline comments,
counter, watermark, and command IDs. Its exact `publication_body` contains the
new ledger payload; preflight restores that payload to `work.ledger_path`.
Do not run the review or increment the counter again. If an artifact is
missing, stop and report it rather than inventing a new count. If the pair
changed, check whether the bot's tracked summary (or,
for an initial publication, a uniquely matching bot review) has exactly the
pending publication's body. If so, recover its review ID and retain the pending ledger and
counter before reviewing the new pair. Otherwise discard the unpublished
artifacts. Keep uncompleted command IDs for the new cycle.

a **new top-level PR conversation comment** whose entire text is
`/review-bot re-review` (case-insensitive, surrounding whitespace allowed).
